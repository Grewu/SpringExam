Using @SpringBootTest(webEnvironment = WebEnvironment.MOCK) loads a web application context and provides a mock web environment. It doesn’t load a real http server, just mocks the entire web server behavior.

WebEnvironment.MOCK gives you some advantages like ease of use or isolation of other factors but it might not be a good integration test practice.

Integration tests should be as similar as possible to the production environment. Considering this, using @SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT) would be a better choice. This approach is closer to test the real application. You can see whether the whole system is going to work as expected.

Here are the transaction propagation behaviors in Spring and their definitions:

  1. REQUIRED: The REQUIRED propagation behavior indicates that the transaction manager must create a new transaction if the calling method does not have a transaction context. If a transaction context already exists, then the method will run within the existing transaction context.

  2. REQUIRES_NEW: The REQUIRES_NEW propagation behavior indicates that a new transaction context must be created for the annotated method, regardless of whether an existing transaction context exists. The existing transaction, if any, will be suspended until the new transaction completes.

  3. SUPPORTS: The SUPPORTS propagation behavior indicates that the transaction manager supports transactions, but does not require them. The method will run within an existing transaction context if it exists, but will run non-transactionally if a transaction context does not exist.

  4. NOT_SUPPORTED: The NOT_SUPPORTED propagation behavior indicates that the transaction manager should not run the method within a transaction context. If a transaction context exists when the method is called, it will be suspended until the method completes.

  5. MANDATORY: The MANDATORY propagation behavior indicates that the method must run within a transaction context. If no transaction context exists when the method is called, the transaction manager will throw an exception.

  6. NEVER: The NEVER propagation behavior indicates that the method should not run within a transaction context. If a transaction context exists when the method is called, the transaction manager will throw an exception.

  7. NESTED: The NESTED propagation behavior indicates that a new transaction should be created, but it will run within an existing transaction context. The nested transaction can be rolled back independently of the outer transaction. If no transaction context exists when the method is called, a new transaction will be created.

This means that the URL patterns that are more specific, like /admin/settings, should appear before more general patterns, such as /admin/**. This ordering is essential because Spring Security evaluates these rules sequentially from top to bottom. When it finds a match, it applies the corresponding access rule and stops further processing. Therefore, if a more general rule appears before a specific one, it may capture requests that should match the specific rule, leading to unintended behavior.


Example of URL Configuration in Spring Security

Here’s a simplified example to illustrate this concept:

  1. @Override
  2. protected void configure(HttpSecurity http) throws Exception {
  3.     http
  4.         .authorizeRequests()
  5.             .requestMatchers("/admin/settings").hasRole("ADMIN")  // Most specific
  6.             .requestMatchers("/admin/**").hasRole("USER")         // Less specific
  7.             .requestMatchers("/**").permitAll()                   // Least specific
  8.         .and()
  9.         .formLogin();
  10. }

In this configuration:

  1. /admin/settings is most specific and requires the user to have an ADMIN role.

  2. /admin/** is less specific, allowing users with the USER role access to all other URLs under /admin/.

  3. /** is the least specific, allowing all users to access other endpoints in the application.

If the rules are placed out of order, Spring Security might apply a broader rule before reaching the more specific one, causing unexpected access results. For instance, if "/admin/**" were placed before "/admin/settings", then any request matching "/admin/settings" would be handled by the "/admin/**" rule instead.

This rule ordering ensures that access control policies are enforced as intended, making the "most specific rule first" approach best practice in Spring Security configuration.
