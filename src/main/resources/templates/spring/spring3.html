Spring AOP provides different types of Pointcut expressions to specify which methods or join points should be advised. Some of the commonly used pointcut expressions are:

  1. Execution - matches join points for method execution.

  2. Within - matches join points within certain types or packages.

  3. This - matches join points where the bean reference is an instance of a given type.

  4. Target - matches join points where the target object is an instance of a given type.

  5. Args - matches join points where the arguments to the method being executed match a given type or expression.

  6. Annotation - matches join points where the subject has the given annotation.

These pointcut expressions can be used alone or in combination to create more complex pointcut expressions.


Here's an example of the execution pointcut expression in Spring AOP:

  1. lessCopy code
  2. @Aspect
  3. @Component
  4. public class MyAspect {
  5.  
  6.     @Before("execution(* com.example.myapp.service.UserService.getUser(..))")
  7.     public void beforeGetUser() {
  8.         System.out.println("Before advice executed for getUser method");
  9.     }
  10. }

In this example, we define an aspect named MyAspect that intercepts calls to the getUser method in the UserService class. The @Before annotation indicates that the method should be executed before the target method is invoked, and the execution pointcut expression specifies the exact method signature to intercept.

What is the root exception class for data access in Spring Framework?

Correct answer

DataAccessException

Your answer is incorrect

SpringDataAccessException

HibernateDataAccessException

JdbcDataAccessException

The main exception class for data access in Spring Framework is DataAccessException. It is a runtime exception, which means it doesn't need to be declared in a method's throws clause.

DataAccessException is the root of the hierarchy of data access exceptions in Spring. It provides a uniform way of handling data access exceptions across different data access technologies such as JDBC, Hibernate, JPA, and more.

DataAccessException has many subclasses that represent specific data access exceptions. Some common subclasses are DuplicateKeyException, IncorrectResultSizeDataAccessException, DataIntegrityViolationException, and CannotAcquireLockException.

By catching DataAccessException instead of specific data access exceptions, the code can handle all data access exceptions uniformly, regardless of the underlying data access technology. This allows for more modular and reusable code.


Springdoc:

public abstract class DataAccessException extends NestedRuntimeException

Root of the hierarchy of data access exceptions discussed in Expert One-On-One J2EE Design and Development. Please see Chapter 9 of this book for detailed discussion of the motivation for this package.

This exception hierarchy aims to let user code find and handle the kind of error encountered without knowing the details of the particular data access API in use (e.g. JDBC). Thus, it is possible to react to an optimistic locking failure without knowing that JDBC is being used.

As this class is a runtime exception, there is no need for user code to catch it or subclasses if any error is to be considered fatal (the usual case).

  • A layered system that organizes each type of server (those responsible for security, load-balancing, etc.) involved the retrieval of requested information into hierarchies, invisible to the client.

  • Code-on-demand (optional): the ability to send executable code from the server to the client when requested, extending client functionality.

Each isolation level prevents zero or more concurrency side effects on a transaction:
